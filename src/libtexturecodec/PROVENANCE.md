# Provenance

This decoder is clean-room: it was written from specification text only. No source
code of any ASTC decoder or encoder (astcenc, Mesa, any GitHub decoder) was read,
copied, translated or paraphrased.

## Specification sources (public)

| What | URL | sha256 of the fetched file | Fetched |
|---|---|---|---|
| Khronos Data Format Specification 1.4.0 (HTML), section 23 "ASTC Compressed Texture Image Formats" | https://registry.khronos.org/DataFormat/specs/1.4/dataformat.1.4.html | `cbf7dd2aa550327615612cd731f388ab38ccd0f1c9728155fd74ffa4ce2b0c98` | 2026-11-22 |
| Plain-text extract of section 23, made with `tools/spec_to_text.py` (tags stripped, one table row per line) | derived from the file above | `e02468bf2f37db2571280e771993a48689ef84ff80a21f5a6b556c796828684b` | 2026-11-22 |

Neither file is in this repository: the first is fetched from the URL (compare the
sha256), the second is made from it with `tools/spec_to_text.py`. Everything the
decoder implements comes from that section: block layout (23.9), block modes
(23.10, tables 160 and 161), colour endpoint modes (23.11), integer sequence encoding
(23.12), endpoint and weight unquantization (23.13, 23.16), LDR endpoint decoding
(23.14.1), weight infill (23.17), weight application (23.18.1), dual plane (23.19),
partition function and `hash52` (23.20), data size determination (23.21), void-extent
blocks (23.22), illegal encodings (23.23), LDR profile (23.24).

The `.astc` container header (16 bytes: magic `13 AB A1 5C`, three block dimension
bytes, three 24-bit little-endian image dimensions) is taken from ARM's public
container description, https://github.com/ARM-software/astc-encoder/blob/main/Docs/FileFormat.md
(documentation, Apache-2.0; read as prose only, no source file).

The Khronos licence allows using the specification to implement the functionality;
no specification text is reproduced here.

## Apple documentation

The decoder uses none. The ImageIO hook (`src/frameworks/ImageIO/src/ImageIOASTC.m`) follows
the names and the NULL-on-error contract of the public CGImageSource documentation on
developer.apple.com (`CGImageSourceCreateWithData`, `CGImageSourceCreateWithURL`,
`CGImageSourceCreateImageAtIndex`, `CGImageSourceCopyPropertiesAtIndex`, `CGImageSourceGetType`,
`CGImageSourceGetStatus`, `CGImageSourceCopyTypeIdentifiers`), read by the design agent on
2026-11-22. The public UTType and system-declared type identifier pages were searched for a
type identifier for ASTC and KTX and name none, so none is used. The pages for the seven
`kCGImageProperty*ASTC*/BC*` constants give only a name, the type `CFString` and availability;
they are not used here. Where these pages are silent (colour space, alpha convention, status
of a bad file, limits) the choices are listed in `GUESS.tsv` as I1 to I7. No Apple SDK file,
header, man page or binary was read for this change.

## Observation of macOS (black box)

The ImageIO hook and the DTC_COMPAT mode follow what macOS 26.7.3 and 10.14.4 give for `.astc` data
through the public ImageIO functions (`CGImageSourceCreateWithData`, `CGImageSourceCopyTypeIdentifiers`,
`CGImageSourceGetType`, `CGImageSourceGetStatus`, `CGImageSourceCopyPropertiesAtIndex`,
`CGImageSourceCreateImageAtIndex`, and the properties of the image they return): type identifier,
pixel format, properties, error behaviour, size limits, the 8-bit values of void-extent colours and the
classification of void-extent blocks. The inputs were the committed vectors, synthetic malformed files
and random blocks of the committed random vectors; only the observable results were recorded
(vd-upstream cristim-mac-evidence.md, section 16). No Apple SDK file, header, man page or binary was
read or disassembled for this, and the decoder was not changed to follow anything but those results.
